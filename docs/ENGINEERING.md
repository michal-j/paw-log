## Public repo and demo mode (DECIDED 16 Oct)
- The repo is public as a concept showcase. Same pattern as the CEO's Movie Shelf and Job Hub: a demo mode with frozen fictional sample data, fully client-side, no backend calls, changes persist only in the visitor's `localStorage`; the demo is served from the same site (for example `/demo`) so every push to `main` deploys both.
- One codebase: a data-access interface with two implementations, `SupabaseRepository` (real) and `DemoRepository` (in-memory plus `localStorage`, seeded from `data/demo/*.json`). A `DEMO_MODE` switch picks one at startup. No feature may call Supabase directly.
- Demo data is fictional and lives in `data/demo/`. The prototype's sample data (`design/prototype/script.js`) is the starting point for it.
- Real data is protected by Supabase, not by repo privacy: row-level security on every table, sign-up disabled (two accounts only), private storage bucket for photos and PDFs, only the anon key in the client.
- CI check: fail the build if the repo contains known real names or a service-role key (list kept outside the repo, in the PM's notes, to avoid publishing it).

## Proposed stack
- Frontend: Vite, React, TypeScript, CSS variables generated from `docs/design-system/tokens.json`; a small i18n layer with EN and PL catalogues seeded from `docs/copy/pawlog-copy-en-pl.csv`.
- Backend: Supabase (Postgres, auth for two users, storage for photos and PDFs, realtime if needed). Row-level security: both household users read and write all rows of their household.
- Hosting: Vercel (static PWA, preview deployments).
- Offline: no service worker since JCB-71 (it stalled Supabase requests in the installed iPhone app, see below); the app shell loads from the network. Offline shell and queued writes are a later decision (JCB-11).
- Tests: unit tests for date and schedule logic; Playwright for the key flows at 390x844.

## Data model (draft, loose)
- `household`, `member` (auth user, household).
- `dog` (household, name). Every other table carries `dog_id`.
- `item` (dog, kind: food | medication | treat | supplement | procedure, name, colour token, day-part default, active from/to).
- `entry` (dog, date, day_part 1 to 7, item, dose_text free-form, state: given | skipped | partial, note, created_by, created_at).
- `event` (dog, date, type: vet | symptom | photo | frontline | deworming | anal_glands | nails | other, title, detail text, issue optional).
- `issue` (dog, name, status). `attachment` (dog, owner entry/event/issue, file path, kind, caption, date).
- `pinned_note` (dog, text, created_by).
- Dates are plain dates in the household timezone; dose text stays free-form.

## Conventions
- TypeScript strict, no `any`. Components named as in the design system; one component per badge/mark kind variant, not per screen.

## Timeline notes (slice 2a, JCB-29)
- `src/timeline/model.ts` derives everything from repository data and is pure: rows (month bands + day rows, newest first, from the first record to `today`), columns and lanes, circle state, badges, rail ticks, scroll lookups. `Timeline.tsx` only renders it. Unit tests: `tests/timeline.test.ts`.
- Rail maths: the rail maps 0..1 onto `span` (the oldest row's top offset), for both dragging and tick placement. The list tail is only `LIST_TAIL_H` (16px), so the oldest day cannot scroll to the top (JCB-62). Instead the Key, the rail highlight and the scrub label follow a *focus* offset: `focusOffset(scrollTop, span, maxScroll)` is the scroll position (top row) for most of the list and, over the last `span - maxScroll` px of scrolling, slides linearly down to `span`, so at the end of the list the focus is the oldest day at the bottom of the screen. Dragging sets the focus directly to the dragged offset (`railTarget`: `focus` = fraction × span, `scrollTop` = `scrollForFocus(focus)`), so the rail reaches every day evenly even when the list can scroll little or not at all (a short log); the rail keeps that focus until the list is scrolled some other way. `maxScroll` is the list's `scrollHeight - clientHeight`.
- Geometry lives in `src/timeline/geometry.ts` (day row 44, month band 28, rail 20, tail 16, column minimums, circle sizes). Row `top` offsets and the rail maths come from these constants; change them together with `timeline.css`.
- Lanes come from logged entries: all food items in one day part share one lane (so Farm Fresh and Ocean Blend sit in the same Dinner column), other items get one lane each, in item order. Items with `hiddenByDefault` (treats, Calmora) are left out until the filters sheet exists. The last day part collapses to width 0 when empty.
- Circles: `DoseMark` takes an item's colour token name (validated against `[a-z0-9-]`) and sets `--mark`; the ring is `color-mix(--mark 80%, ink)`. Badges: `EventBadge`, one component, tokens `badge-<kind>-*`. The `mini` badge size (calendar) still uses 9px/11px text: no type token exists for it. Event types without a designed badge (anal glands, nails, other) are not shown yet.
- Rows are not interactive yet (day view is a later slice); each row carries a visually hidden summary for screen readers; symptom titles matching a known type (`sx_*` copy keys, by English name) are read in the UI language (`src/timeline/labels.ts`). The rail is 20px wide and scrubbing starts only on it: a wider hit area would have to overlap the Events column with `touch-action: none` and turn vertical swipes there into scrubbing.
- Months with no records (the prototype's 44px "Backfill" bands) are not shown: backfill is part of the add flow.

## Backend notes (slice 2b, JCB-35)
- Status: code, migrations and tests are done; the Supabase project does not exist yet. The CEO follows `docs/runbooks/supabase-setup.md` to create it, apply the migrations and run the bootstrap.
- Schema (`supabase/migrations/`): `household`, `member` (household, auth user), `dog`, `item`, `schedule_slot`, `entry`, `event`. Every data table has `dog_id`; dates are `date`; dose is free text; `entry.state` is given | skipped | partial; `event.type` is a key (vet, symptom, photo, frontline, deworming, anal_glands, nails, note, other) with free-text `title`/`detail` and optional `intensity` (small | medium | large). `item.position` orders timeline lanes. Composite foreign keys stop an entry or slot from pointing at another dog's item or slot.
- Schedule slots: the plan (item, day part, usual dose, active period); one item can have several. `entry.schedule_slot_id` is null for an unplanned entry; a unique index on (dog_id, date, schedule_slot_id) allows one entry per slot per day, so two people filling in the same day cannot double-log. The repository turns that conflict into `DuplicateSlotEntryError` (DemoRepository applies the same rule). `item.default_day_part` stays for lane order and the demo, which derives one slot per item.
- Triggers set `created_by` on insert (never changeable) and `updated_by`/`updated_at` on every write; the client never sends them.
- RLS (`20261016120100_row_level_security.sql`): table privileges are revoked from `anon` and granted to `authenticated` only as needed; policies call `private.is_household_member` / `private.can_access_dog` (SECURITY DEFINER, pinned `search_path`, in a schema the Data API does not expose). household, member, dog: select only. item, schedule_slot, entry, event: select/insert/update/delete with USING and WITH CHECK, so rows can neither be read nor moved across households.
- Tests: `supabase/tests/database/rls.test.sql` is pgTAP. `npm run test:db` runs it in PGlite (WASM Postgres), with `tests/db/supabase-stub.sql` (roles, `auth.users`, `auth.uid()`, Supabase default grants) and `tests/db/tap-shim.sql` (the pgTAP functions used). On a machine with Docker, `npx supabase start` then `npx supabase test db` runs the same file against real Supabase. Not covered by PGlite: Supabase's auth server and PostgREST; those are manual cases in TEST-CASES.
- Auth (CEO decision, 16 Oct): e-mail + password, `signInWithPassword`. One screen with a Show/Hide toggle; fields use `autocomplete="username"` / `"current-password"` so iPhone Keychain can fill and save them. No sign-up and no in-app password reset: sign-ups are disabled in the dashboard, the CEO creates both users there (auto-confirmed) and resets passwords there or with the SQL in the runbook. No e-mail is ever sent, so no SMTP setup. `detectSessionInUrl: false`. Session in `localStorage` under `pawlog.auth`, refreshed automatically; home-screen web apps keep their storage across restarts. Sign-out uses `scope: 'local'` (this device only). Wrong password and unknown e-mail give the same message.
- Structure: `src/auth/` holds config (`readSupabaseConfig` validates `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`, rejecting placeholders and non-https), the client factory, `AuthService` (interface plus Supabase implementation, errors mapped to a few kinds), `AuthGate`, `SignIn`, `ConfigError`. `RealApp.tsx` is the only place that wires client, auth and repository, and `main.tsx` lazy-loads it only outside demo mode. Components never import supabase-js.
- `SupabaseRepository.today()` is the device's local date (both members share one timezone). New entry and event ids must be UUIDs (`crypto.randomUUID()`); the repository refuses others before calling the server. Lists are read in pages of 1000 (PostgREST's default cap).
- After sign-in, `AuthGate` calls `getDog()` first: an account with no household gets a message, not an empty timeline. Offline, supabase-js retries reads a few times, so the first screen can take several seconds before the (empty) timeline appears; offline support is JCB-11.
- Sign-in UI reuses the Card, Button and Sheet input recipes. The design system has no text-field or password-field component yet; inputs follow the Sheet README (50px, 16px text so iOS does not zoom), and the Show/Hide toggle sits inside the password field with a 44px hit area.

## Day view notes (slice 3a, JCB-30)
- Routing: `src/routes.ts`, no router library. `<base>/` is the Timeline, `<base>/day/YYYY-MM-DD` a day; `base` is `/demo` on the demo path, else empty. Anything else (bad shape, impossible date) is rewritten to the Timeline with `replaceState`; a well-formed date outside the records (before the first record or after today) is rewritten once the data is loaded.
- History: opening a day stores the Timeline's list `scrollTop` in the Timeline entry's `history.state`, then pushes the day with `{ fromTimeline: true }`. Back (in-app) calls `history.back()` when that flag is set, else replaces with the Timeline. Previous/next use `replaceState`, so one Back always returns to the Timeline. The Timeline restores `initialScrollTop` in a layout effect once rows exist and the list has its height.
- Each Timeline row is an `<a href>` overlay (`.tl-row__link`, covers the hairline so the target is 44px) holding the screen-reader summary; modified clicks (new tab) are left to the browser.
- `src/day/model.ts` is pure: `groupDayParts` (all items, `hiddenByDefault` ignored; food first, then item order), `groupDayEvents` (vet cards, one symptoms card, then Frontline, deworming, photo, other types), `dayBounds`/`stepDay`, `buildDay`. Unit tests: `tests/day.test.ts`.
- Prev/next are buttons with `aria-disabled` at a bound (stay focusable, announced as unavailable). The date heading is in an `aria-live="polite"` region so stepping is announced.
- Out of scope here, so not rendered: the add bar, per-part + buttons, jump to date, attachments, tracked-issue link on photo cards. Event types without a designed badge (anal glands, nails, other) show as a card without a badge.
- Data text (item names, dose text, event titles and details) is shown as stored; only symptom titles of known types are translated (`symptomLabel`). The demo data is English, so in Polish those strings stay English.

## Logging and the usual day (slice 3b, JCB-39)
- Design: `design/proposals/add-edit/` (JCB-25 round 2, approved) plus CEO feedback: the item can be changed when editing; "All given" per part; a Menu in the header; editable day-part times.
- Schema (`supabase/migrations/20261016140000_logging_usual_day.sql`, a new migration; earlier ones are untouched): structured amounts on `entry` and `schedule_slot` (`amount` numeric > 0, `unit` one of pill, capsule, sachet, ml, drop, can, tray, g, piece, `flavour` text); `entry.dose_text` stays for rows written before (shown when `amount` is null; new rows leave it empty). `item.default_unit`, `item.flavours text[]`, `item.conversion_unit` ('bars') + `conversion_size` (ml per bar). `event.props jsonb` (symptom properties as keys) and `event.also_done text[]` (built-in keys anal_glands, nails; since JCB-89 also the dog's own services as typed text, see below). `day_part (dog_id, part, usual_time)` with RLS like the other data tables; parts without a row use the defaults in `DEFAULT_DAY_PART_TIMES`. The entry → slot foreign key is now `on delete set null (schedule_slot_id)`: removing a usual-day slot keeps its entries as unplanned ones.
- Own vet services (JCB-89, `20261022120000_vet_own_services.sql`): `event.also_done` allows at most 10 items, each trimmed and 1-40 characters (check via `public.also_done_valid`, since a check cannot hold a subquery). No table: like clinic chips, the chips of a new visit are the two built-ins plus the own services of this dog's earlier visits, most recent first (`src/log/services.ts`); a service leaves the list when no visit uses it. `AlsoDone` is a string; both repositories store `cleanAlsoDone(...)`.
- Usual day = `schedule_slot`. A change from a date ends the old slot the day before and inserts a new one (`changeFrom` in `src/log/plan.ts`); a slot that starts on or after that date is updated in place. Changing only the course length keeps the slot's start and counts 7/14 days from it. "Remove from this day on" ends the slot, or deletes it if it has not started. A course is explicit: `schedule_slot.is_course` (with an end date) is set only by "How long" (7 days, 14 days, an end date) on the Usual day; "day n of m" shows only for courses. A slot ended by a change from a date or a removal has `active_to` but is not a course.
- Matching (`matchDay`): an entry fills the slot it names; an entry that names no active slot (older rows, or a slot replaced from a date) fills an open slot of the same item and part. Planned rows are the active slots nobody filled; a part is due when its usual time has passed (`partDue`; past days are always due). Fill and Given call `Repository.addPlannedEntries`, which inserts with ON CONFLICT DO NOTHING on the (dog_id, date, schedule_slot_id) index, so filling never overwrites and two phones cannot double-log; it returns the inserted ids for Undo.
- Undo: every write in `src/log/actions.ts` returns its inverse (delete → save the old row again with the same id, fill → delete the inserted ids, usual-day change → restore the saved slots or delete the new ones). The toast lasts 8 s with Undo, 5 s without (`TOAST_UNDO_MS` and `TOAST_MS` in `LogProvider`); deferred work tied to Undo (photo file deletion) runs when the toast ends, so it follows the same constant. Writes are guarded in flight (`useBusy`): a double tap on Save, Delete, Given, All given or Fill writes once, and a Given/Fill that adds nothing keeps the current toast and its Undo. (JCB-43: no space is reserved after a fill any more; see below.) Given is offered on every planned row (also Later today); Fill and All given cover only the due ones. + Add without a part opens on the part of the day it is now. A restored entry gets the restoring user as `created_by` (the trigger stamps inserts).
- UI state: `LogProvider` (`src/log/LogProvider.tsx`) loads everything the Timeline, Day view, Usual day and sheets read (items, slots, entries, removed slots, events, day-part times, settings) and reloads after each write; it also holds the open sheet and the toast. Components only call the Repository through it or `actions.ts`.
- Amount display (`src/log/amount.ts`): fraction chips match within 0.005; anything else is a comma decimal (both languages, as the reviewed copy writes "0,15 ml"). Unit labels: EN singular up to 1, plural above; PL one / few (2-4, not 12-14) / many / fraction forms, from the draft gaps CSV. ml and g always show a decimal.
- Symptoms (`src/log/symptoms.ts`): a known symptom is stored under its English name in `title` (so the Timeline's `symptomLabel` translates it); Poo, Vomit and Leakage have their own property chips stored in `props`, every other symptom (including a typed one) has Intensity stored in `intensity`.
- Copy: `docs/copy/copy-proposal-add-edit.csv` (the design's strings) and `docs/copy/copy-proposal-log-gaps.csv` (strings the design did not have: "All given", "Menu", unit plural forms), both drafts merged by `npm run generate`. Frontline in the "other" type picker uses the reviewed "Frontline (monthly)".
- Demo: `data/demo/schedule.json` is the fictional usual day; the demo's date is frozen at 15 Oct but the time of day is the device clock, so "up to now" behaves like the real app. Storage key `pawlog.demo.v2`.
- Not done here: attachments (photos, PDFs), backfill of several days (sketch only in the design), offline queued writes (JCB-11). Items added under "Other" got `mark-neutral` at the time; JCB-59 gives them a colour.

## Real-data blockers (JCB-43)
- **Reproduce on the real path.** `tests/harness/fakeBackend.ts` is a fake Supabase backend: the real supabase-js client (custom `global.fetch`) and the real `SupabaseRepository` talk to a PostgREST-like handler on PGlite with `tests/db/supabase-stub.sql` and every migration applied, RLS on, the signed-in user as `auth.uid()`. It supports what the repository uses (select with eq/neq/gte/lte/is/in/or filters, order, range; insert and upsert with `on_conflict`, merge or ignore duplicates, `columns`, `return=representation`; PATCH; DELETE) and answers errors like PostgREST (23505 → 409 and so on). `failNext(n)` simulates offline, `setLatency` slow or overlapping answers. It never calls a network. Fictional seed in `seedHousehold`.
- **Contract tests** (`tests/contract.test.ts`) run the same scenarios against `DemoRepository` and `SupabaseRepository` (save, edit in place, duplicate slot, fill and its Undo, delete and Undo, removed for the day, settings, day-part times, slots, items). A behaviour change in one implementation must pass for both. **Real-path app tests** (`tests/realpath.test.tsx`) drive the whole app on the fake (a fresh database per test, about 1 s each).
- **Browser harness** (dev only, not built): `npx vite --port 5180`, open `/harness.html`. The real app with `AuthGate` (a fake signed-in user) on the fake backend in the tab; `?start=YYYY-MM-DD` sets the usual-day start (default 10 days ago). Data lives only in the tab; a reload starts again from the seed on the same screen (a session cookie makes the dev server answer every page with `harness.html`; `/harness.html?off` leaves harness mode). `window.harness.backend.sql('select …')` reads the database.
- **Root causes** of the data bugs, all client-side (the server logs showed every write succeed): (15) an edit, or logging a planned row, that changed the item (or part) looked up a slot for the *new* item only, found none and cleared `schedule_slot_id`, so the old slot showed "not logged" again next to the changed row; (13) a delete removed the slot's only entry, so the slot was open again; (1, 5) the Menu saved a day-part time on every input event, the writes ran concurrently (the last to land won, not the last typed) and each reload reset the field under the finger; (3) after saving on a day before the first record the Day view judged the date on the records still loading and bounced to the Timeline (and a failed reload kept stale data silently); (4) the Timeline loaded on its own every time it mounted and rendered nothing until that finished, or ever if it failed.
- **Slot on save** (`slotOnSave` in `EntrySheet.tsx`): the new item's own open slot in that part first; otherwise the slot the sheet was opened for (the planned or removed row's slot, or the one the edited entry fills) keeps it, if the date is unchanged and nobody else fills it.
- **Removed for the day**: deleting an entry that fills a slot (`act.deleteEntry` with the slot) calls `Repository.removeFromDay`, which turns the row into a marker in place (same id, `state = 'removed'`, `schedule_slot_id` set). `listEntries` never returns markers; `listRemovedSlots` does. `matchDay` counts a removed slot as filled (and reports it in `removed`), so it is neither planned nor due, and the unique (dog, date, slot) index makes `addPlannedEntries` skip it on both phones. JCB-60: the Day view never draws a marker as a row (`DayPartGroup.removed`, not `rows`), so deleting any entry looks the same; one quiet line at the bottom of the day counts them with Restore (`act.restoreRemoved`: deletes the markers, so the slots are planned again; Undo re-creates them, skipping a slot logged meanwhile). The Timeline reads only `listEntries`, so it never draws markers. The entry form still reuses a marker's id when opened with `replaces`. If another entry already fills that slot, the delete is a plain delete. Removing a slot from the usual day clears the marker's slot id; such markers are never shown.
- **Writes are queued** in `LogProvider.run` and Undo: one at a time, in the order asked, so the last change wins. Date and time settings use `CommitInput` (save on blur, Enter or unmount; a reload never overwrites what is being typed; the saved value shows until the reload arrives).
- **Loading**: a failed load keeps what is shown, sets `loadFailed`, and retries every 4 s and on `online`/`visibilitychange`. The Timeline renders from `records`, with Try again when nothing has loaded. `ErrorBoundary` around the app shows Reload instead of a blank page. `Records.version` is the reload the records came from; the Day view only judges a date out of range on records of the current version. The Supabase client reads with `cache: 'no-store'`.
- **Log start**: `dog_settings.log_start` (new table, RLS like `day_part`; Menu > Log starts on, saved on commit). `logStartOf`: the setting, else the earliest record or slot start, else a year back; never later than the first record or today. Timeline rows and Day view bounds run from it to today, empty days included. Long logs (over 120 rows) render only the rows within 900 px of the viewport, with two spacer rows keeping the fixed row geometry, so the rail maths is unchanged.
- **Past days for a usual-day change**: after a slot is added or changed from a date before today (not a course-length-only change), `backfillDays` lists its open past days (start to yesterday, within its period; logged or removed days left out) from the reloaded records; `BackfillSheet` asks once; Yes calls `addPlannedEntries` and reports the days already logged (`total - added`); Undo deletes what it added.
- **Items** (`src/log/items.ts`): a new item's colour is `nextColour`: the first item colour token (food-*, med-*, treat, in tokens.json order; not mark-neutral) no item uses, else the least used. `ColourPicker` swatches offer only those tokens (new items; on the Usual day also an existing item). Food takes any flavour; a new one ("Add flavour") is appended to the item's `flavours` on save (Undo restores the item). A new entry form starts from `lastUsed` (latest entry of the kind by date, then part). The Usual day's + opens the Food / Medication choice, then `SlotSheet` with `group`.
- **Fill**: the banner only on a day with no entries; otherwise a quiet ghost button under the parts. A fill keeps the day parts where they were on screen when the scroll position allows (no reserved space).
- **Migration** `20261017120000_removed_entries_log_start.sql` (new file; the three earlier ones are applied in production and unchanged). Copy: `docs/copy/copy-proposal-blockers.csv` (draft, pending CEO review).
- Not covered by the harness: Safari's own rendering of date and time inputs and the iOS keyboard (manual cases 59, 63).

## Item colours and the item editor (JCB-59)
- **Root cause** of grey items in production: JCB-43 only chose a colour (`nextColour`) when an item was created. Items created before it (the first "Other" items, saved as `mark-neutral`) were never given one, there was no data migration, and the only colour control for an existing item was inside the Usual day's slot form (only for items with a slot, mixed with "change from a date"). Editing an entry and picking Other also still created the new item as `mark-neutral`.
- **Auto colour** (`nextColour(items, kind)` in `src/log/items.ts`): the least used of `AUTO_COLOURS` (the item colour tokens minus `AUTO_EXCLUDED` = med-calmora, which reads as grey next to mark-neutral; still offered in the swatches), on a tie a token of the item's own kind first (food-* for food, med-* for medication/supplement/procedure, treat for treats), then tokens.json order. So: an unused colour of its own kind, else an unused one of the rest, then cycling.
- **On load** `LogProvider` passes items through `withItemColours`: an item whose colour is not one of `ITEM_COLOURS` (mark-neutral, or an unknown token such as `food-old`) shows the colour the migration would give it (lane order: position, created_at, id, which is the items query's order; each takes `nextColour` of every colour shown so far). Colours shown for items that are still grey are remembered for the session (`shown`), so saving one item never changes the colour shown for another. The next save of the item stores its colour.
- **Migration** `20261018120000_item_colours.sql` (data only, new file; earlier ones untouched): the same rule per dog in SQL; items with an item colour are never touched, so it is idempotent. Its palette and exclusions must equal `ITEM_COLOURS` / `AUTO_EXCLUDED`; `tests/migrations.test.ts` checks that, fixed cases, a second run, cycling, and app↔migration equality on mixed data with position/created_at/id ties (PGlite, migrations applied up to it, fictional rows).
- **Item editor** `src/log/ItemSheet.tsx`: name (required), colour (item colour swatches), default unit (the kind's units), flavours (tap a chip to remove, type and Add; a typed flavour not yet added is kept on Save). Undo restores the item. Entries and usual-day rows keep the flavour text they were logged with. Opened by "Edit item" in the label row of the entry form's item picker (when an item is picked) and on a Usual day item's sheet (also in its item picker); the editor replaces that sheet in place and returns to it with the form as it was (`editing` state in `EntrySheet` / `SlotSheet`). The Usual day item sheet no longer has its own colour swatches (two colour controls on one item could overwrite each other); a new item under Other still picks its colour there.
- New items from every path (entry form Other, also while editing an entry; Usual day Other) take `nextColourFor(records.items, group)`, worked out on every render until a swatch is picked, so it is never a colour another item just took (also after Edit item).

## Save never hangs (JCB-71)
- **Root cause**: in the installed iPhone PWA, a request running when iOS suspends the app can stay pending forever after it resumes (no answer, no error). supabase-js 2.117 is lockless (no `navigator.locks`) and already stops/starts auto-refresh on `visibilitychange`, but it single-flights the token refresh: every `getSession()` (and so every database call, through `fetchWithAuth`) waits on the one refresh in flight. A refresh lost that way (the server answered 200; the app never heard) blocked every later write before it was sent, so the `useBusy` guard never let go and only a restart helped.
- **Fix**: `src/auth/resilientFetch.ts` is the client's `global.fetch` (auth and PostgREST): each request is aborted after 10 s (`REQUEST_TIMEOUT_MS`), and when the app returns to the foreground every request that ran while it was hidden is aborted at once (supabase-js retries the refresh); the promise settles even if the underlying fetch ignores the abort.
- **Defence in depth**: `withTimeout` (`src/data/timeout.ts`) wraps the real repository (`createRepository`, the harness, the fake in tests): any call not settled in 15 s (`OPERATION_TIMEOUT_MS`) rejects with `RepositoryError` code `timeout`. `LogProvider.run` then reloads and shows "Couldn't save · Try again" (`errSave`); the sheet stays open and Save works again. A slow read on a very slow connection is retried by the load-retry loop.
- **Retries never double**: sheets that create rows (Entry, Event, Slot, Pinned, Condition; new items from Other; conditions named in the Event sheet get their id when picked, in form state) take their ids from `useDraftIds`, made once per open sheet, so a retry upserts the same rows even when the first attempt reached the server late. Fill/Given/past days rely on the one-entry-per-slot index; deletes, reorders, day-part times and settings are idempotent.
- **Reopened 18 Oct, the real cause**: in the foreground, one write got through after each app start and the next never reached the server (edge logs: every request that arrived succeeded, session valid). On the real path (`tests/saveSequence.test.tsx`: app auth settings, six saves of different kinds in a row, and a different save after a timed-out one) nothing in the app holds writes back. What stood between the app's `fetch` and the network was the Workbox service worker: a page it controls hands it every request first, cross-origin Supabase calls included, although it only cached the app shell and let them through. On iOS that hand-off can stall once the system has stopped the worker (it stops idle workers after a short while), and only a restart (a fresh worker) helps. So the app runs without one: `VitePWA` keeps the manifest but builds a self-removing `sw.js` (`selfDestroying`, `injectRegister: false`) that unregisters the old worker on phones that have it, clears its caches and reloads the page once; `src/main.tsx` calls `removeServiceWorkers()` (`src/serviceWorker.ts`) as well. Add to Home Screen does not need a worker on iOS. Lost: the shell (and the demo) no longer open offline (JCB-11). Test: `tests/serviceWorker.test.ts`.
- **Reopened again 18 Oct evening (after the worker went)**: 1–3 saves get through, then the next never reaches the server until a restart; usually the first save after switching views; switching wifi/mobile data helps for a while. Not reproducible off the iPhone. Suspected (not proven): WebKit keeps reusing a dead pooled connection to the Supabase host (one HTTP/2 or HTTP/3 connection per host carries every request, `<img>` thumbnails included); aborting a fetch does not close that connection. Ruled out on the real path: the client awaits (no auth lock in supabase-js 2.117, the write queue releases on timeout) and the "no `POST event_condition`" clue (that is simply an event with no condition links; edits and new events from a condition page keep their links).
- **Stall recovery**: `resilientFetch` sends a PostgREST write (non-GET under `/rest/v1/`, string body) that got no answer in 6 s (`WRITE_STALL_MS`), was lost in the background, or failed with a network error once more as a new request (own signal, `cache: 'no-store'`, `keepalive: false`, `priority: 'high'`), limited to 8 s (`WRITE_RETRY_MS`); 6 + 8 stays under the 15 s `withTimeout`. Safe because every write is idempotent (upsert by id, delete by id, update to a value, the restore RPC upserts). Never retried: reads (the load-retry loop covers them), auth (refresh tokens are single-use), storage, caller aborts. JS cannot force a new connection to the same host; if the request log shows retries stalling too, the next step is a same-origin proxy or keeping the connection warm (needs a decision).
- **Request log** (`src/diag/requestLog.ts`, `src/diag/RequestLogPanel.tsx`): every attempt through `resilientFetch` plus background/foreground and online/offline, last 30 rows: time, method, table (or `rpc <fn>`, `auth <endpoint>`, `storage`), retry mark, duration, outcome (status, no answer, lost in background, cancelled, network error) and the protocol of the latest request to that host when Resource Timing exposes it. No query strings, ids, bodies or headers. Hidden: `?diag=1` / `?diag=0`, or five quick taps on the Menu heading (the installed app has no address bar); while on, the log is kept in `localStorage` (`pawlog.diag.log`) so it survives a restart. Menu shows it with Copy and Clear.
- **Harness**: `backend.hangNext(n, which)` holds requests (they ignore aborts, like a lost one) until `backend.release()`; the fake answers `POST /auth/v1/token`. `/harness.html?diag=1` shows the request log. Tests: `tests/resilientFetch.test.ts`, `tests/saveHang.test.tsx`, `tests/requestLog.test.tsx`.

## Photos (JCB-7)
- Design: `design/proposals/pinned-tracked/` (CEO-approved): PhotoThumb, PhotoStrip, PhotoPick, PhotoViewer with Compare. PDFs later.
- **Schema** (`20261020120000_photos.sql`, new file): `attachment` (dog, event_id, kind `photo`, storage_path, width, height, taken_at = wall-clock time from the photo, caption, position, stamps). Composite FK `(event_id, dog_id)` → `event`, on delete cascade (deleting an event deletes its photo rows). `storage_path` must equal `<dog_id>/<id>.jpg` (check). RLS like the other data tables.
- **Storage**: private bucket `photos` (JPEG only, 5 MB a file). Files: `<dog_id>/<attachment_id>.jpg` (long edge ~1600 px) and `<dog_id>/<attachment_id>.thumb.jpg` (480 px). `storage.objects` policies `pawlog_photos_*`: select/insert/update only when `private.can_access_dog(private.photo_object_dog(name))` (names that are not exactly `<uuid>/<uuid>[.thumb].jpg` give null and are refused); delete additionally only when the attachment row is gone. The app reads through signed URLs (`PHOTO_URL_TTL_S` = 10 min, reused in memory until 2 min before expiry, so the browser can cache the image; objects are uploaded with a 1-year Cache-Control because a path never gets other content).
- **Device**: `src/photos/resize.ts` reads the EXIF date (DateTimeOriginal, else DateTimeDigitized, else DateTime), decodes with the camera orientation, draws onto a canvas and encodes JPEG (0.82 full, 0.75 thumb). Re-encoding keeps no metadata, so GPS never leaves the phone; the date is kept in `taken_at`. The form uses its date as the event date (editable; never after today). The file input is `accept="image/*"` without `capture`, so iPhone offers library, camera and files.
- **Uploads** (`src/data/upload.ts`, QA fix): each file goes to a signed upload URL for its fixed path (the signing call is an ordinary 10 s request) through XMLHttpRequest, which gives up only after 20 s without upload progress or 120 s in all (fetch fallback: 15 s + 1 s per 20 KB, max 120 s). `uploadPhotoFiles` is exempt from the 15 s `withTimeout` (`OWN_LIMITS`) and from `resilientFetch`'s 10 s. Tests: `tests/upload.test.ts`, the slow and stalled cases in `tests/photosApp.test.tsx`.
- **Writes** (`act.saveEvent` with `PhotoChanges`): upload files first (upsert, same paths every time), then conditions, event, photo rows. Ids come from `useDraftIds`, so a retry after a time-out re-uploads to the same paths and upserts the same rows. Delete: the row goes (a photo event with no photo left goes too); the files stay so Undo works, and are removed by `Undo.commit` when the toast goes away without Undo (`LogProvider` settles a toast on time-out, replace, dismiss or unmount). Undo of a new photo removes its files at once. Files left by an interrupted save or a closed app are harmless orphans (private, policy-protected).
- **UI**: `src/photos/` — `PhotoSheet` (+ Add → Photo, condition strip's Add photo, Edit from the viewer or a photo card; Change replaces the picture with a new attachment), `PhotoViewer` / `PhotoCompare` (overlays in `LogProvider.overlay`; viewer pages through a condition's photos oldest first, or a day's photos in card order; swipe, arrows, keyboard), `PhotoParts` (thumb, pick tile), `usePhotoUrl` (batches URL requests per tick). Symptom, vet visit and note forms have a Photos field. Condition page: strip + Compare; Tracked list cards: latest photo + count. Timeline: one camera badge per day with any photo (`badgesFor(events, withPhotos)`); row geometry unchanged.
- **Demo**: two bundled fictional drawings (`data/demo/photos/*.svg`, served with the app, no network) on the Lump A photo events; photos added in the demo are kept as data URLs under `pawlog.demo.photo-files.v1` (in memory when localStorage is full; the form says so in demo mode).

In the browser harness, `SupabaseRepository`'s `displayUrl` turns signed URLs into blob: URLs (the fake has no address).
